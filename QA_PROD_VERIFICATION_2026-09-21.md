## 3) Bug Report

### BUG-QA0921-01 — Chat read-receipt icon does not reflect actual read status in production (fix present in source, not observed live)

- **Severity:** Medium (cosmetic / informational integrity issue — does not corrupt data, but misleads the sender about whether the other party has actually seen their message)
- **Priority:** Medium
- **Module:** Chat / Messaging (`apps/web/components/chat/chatpage.tsx`)
- **Status:** Confirmed (reproduced twice, including after a full hard page reload)

**Summary:** In production, every one of the customer's own sent chat messages renders the `CheckCheck` (double-check, "read") icon, regardless of the message's actual `isRead` value returned by the API. This is the exact symptom the commit `0ac1aea` ("fix: 4 bugs confirmed in QA session 2026-09-17..20") claims to have fixed, and the fix (`message.isRead ? <CheckCheck/> : <Check/>` at line 380 of `chatpage.tsx`, confirmed present in the current `main` branch source) does **not** appear to be reflected in the live production frontend build.

**Steps to reproduce:**
1. As a customer, send a chat message on an order (message A).
2. As the shop owner, call `PATCH /messages/:orderId/read` (marks message A as read).
3. As the customer, send a second chat message (message B) — leave it unread by the shop.
4. Confirm via `GET /messages/:orderId` that message A has `isRead:true` and message B has `isRead:false`.
5. As the customer, open `/chat` in a browser, open the conversation, and inspect the checkmark icon rendered next to each of your own messages (both by visible icon and by inspecting the rendered `<svg class="lucide lucide-check-check">` / `lucide-check` DOM class).
6. Hard-reload the page (`location.reload()`) and repeat step 5 to rule out stale client-side cache.

**Expected result:** Message A (read) shows the double-check icon; message B (unread) shows the single-check icon.

**Actual result:** Both message A and message B show the double-check (`lucide-check-check`) icon, both before and after a hard reload.

**Evidence:**
- API response at time of DOM check: `[{"content":"QA test message #2 - should be UNREAD","isRead":false},{"content":"QA test message from customer","isRead":true}]`
- DOM query at the same moment: both messages' checkmark `<svg>` elements have class `lucide lucide-check-check` (no plain `lucide-check` found anywhere on the page).
- Current `main` branch source (`apps/web/components/chat/chatpage.tsx:380`): `{isMine && (message.isRead ? <CheckCheck size={11} /> : <Check size={11} />)}` — this is the *correct* logic, and it is on `main` (commit `0ac1aea`, merged via PR #44, which is the current `HEAD` of `main` per `git log`).

**Root cause hypothesis (not confirmed, needs dev-side investigation):** Since the source code on `main` already contains the fix, but the live production frontend does not exhibit the fixed behavior, the most likely explanation is a **stale or incomplete Cloudflare Pages/Workers deployment** — i.e., the production build being served was built from a commit prior to `0ac1aea`, or the deploy pipeline for `apps/web` did not pick up this specific file's change (e.g. a cache issue in the build step, or the relevant JS chunk being served from an edge cache that wasn't purged after deploy). This should be checked by comparing the deployed Worker's build/commit identifier against `origin/main`'s current `HEAD` (`61265ea`), and by verifying `apps/web`'s deploy pipeline actually ran successfully after PR #44 was merged. It is also possible (lower likelihood, since the ternary logic itself is simple and correct) that there is a separate client-side data-freshness bug (e.g. the initial message list fetched on page load is never updated after the `PATCH .../read` call from the *other* party, so the sender's own view of `isRead` is only ever correct if they reload after the recipient has already read it before the page was first loaded) — but this was ruled out for this specific repro since message B was created and inspected in the same session, after message A was already confirmed read, and a hard reload did not change the result.

**Recommendation:** Verify/trigger a fresh production deploy of `apps/web` and re-test. If the bug persists after a confirmed fresh deploy, it is a real client-side logic bug, not a deploy-lag issue, and should be re-opened as a code-level defect.
